# แผนการตรวจ — เลือกร้านหลายร้าน เก็บเป็นแผน และติดตามว่าตรวจร้านใดแล้ว

วันที่: 3 กันยายน 2026

## ปัญหา

ระบบวันนี้ค้นร้านยาจาก อย. ได้ทีละร้าน เลือกหนึ่งร้านแล้วส่งต่อไปกรอกบันทึกการตรวจ
แต่งานจริงของสำนักงานเริ่มจากการทำ *แผนการตรวจ* — รายชื่อร้านของวันนั้นทั้งชุด
พิมพ์เป็นตารางถือติดมือไปตรวจ (ตัวอย่าง: `แผนการตรวจ 27 สค 69.docx` — 7 ร้าน
คอลัมน์ ลำดับที่ / ชื่อสถานที่ + เวลาทำการ + พิกัด / ประเภทใบอนุญาต + เลขที่ /
สถานที่ตั้ง / ผู้รับอนุญาต / ผู้มีหน้าที่ปฏิบัติการ พร้อมเลข ภ. ทุกคน)

วันนี้แผนนี้พิมพ์มือใน Word ทั้งที่ข้อมูลทุกช่องมีอยู่ในระบบแล้ว และเมื่อออกตรวจจริง
ไม่มีที่บันทึกว่าร้านไหนกรอกบันทึกไปแล้ว

## สิ่งที่จะสร้าง

1. เลือกร้านได้หลายร้านจากหน้าค้นหา แล้วใส่ลงแผนของวันที่หนึ่ง
2. แผนเก็บบนเซิร์ฟเวอร์ ทุกคนในทีมเห็นชุดเดียวกัน
3. ตารางแผนบนเว็บ หน้าตาตรงกับไฟล์ Word ที่สำนักงานใช้
4. สถานะ "ตรวจแล้ว" ต่อร้าน ติดอัตโนมัติเมื่อสร้างไฟล์บันทึกการตรวจ แก้ด้วยมือได้
5. ส่งออกแผนเป็น PDF และ Word

## ขอบเขตที่ตัดออก

- ไม่มีระบบผู้ใช้รายคน (ใครแก้อะไรไม่บันทึก) — กันด้วยรหัสผ่านเดียวของสำนักงานก่อน
- ไม่มีการมอบหมายงานให้เจ้าหน้าที่รายคน
- ไม่แก้หน้าตาบันทึกการตรวจ (`form.html`) — เพิ่มแค่การรายงานสถานะกลับ
- ไม่มีปฏิทิน ไม่มีการแจ้งเตือน

## 1. ข้อมูล

หนึ่งแผนคือหนึ่งเอกสาร JSON

```js
{
  id: '2569-08-27',            // วันที่ตรวจแบบ พ.ศ. เป็นกุญแจ ซ้ำได้ต่อท้าย -2
  title: 'แผนการตรวจสถานที่ประกอบวิชาชีพเภสัชกรรม',
  date: '2569-08-27',
  createdAt: '2026-09-03T…',
  updatedAt: '2026-09-03T…',
  items: [
    {
      newCode: '…',            // กุญแจร้านของ อย.
      order: 1,
      placeName, licenseType, licenseNo, address,
      licenseeName, openHours,
      lat, lng,
      pharmacists: [
        { name, openHours, licenceNo, licenceSource }  // auto | ambiguous | none | manual
      ],
      status: 'planned',       // planned | done
      statusSource: 'auto',    // auto | manual
      note: '',
      syncedAt: '2026-09-03T…'
    }
  ]
}
```

**รายการในแผนเป็นสำเนา ไม่ใช่การอ้างอิง** ตอนใส่ร้านเข้าแผน ระบบคัดลอกข้อมูลจาก อย.
ลงในแผนเลย แผนคือเอกสารของวันนั้น ถ้า อย. แก้ข้อมูลภายหลัง แผนที่พิมพ์ไปแล้วต้องยังตรงกัน
การดึงข้อมูลใหม่เป็นการกระทำที่เจ้าหน้าที่สั่งเอง (ปุ่ม "อัปเดตจาก อย.") ไม่ใช่ผลข้างเคียง

## 2. ที่เก็บ

`src/plans-store.js` เปิดหน้าที่สี่อย่าง: `list()`, `get(id)`, `save(plan)`, `remove(id)`
มีสองการทำงานเบื้องหลัง เลือกด้วย `PLANS_STORE`

| ค่า | เบื้องหลัง | ใช้เมื่อ |
| --- | --- | --- |
| `blob` | Vercel Blob (`@vercel/blob`) ที่ `plans/<id>.json`, `access: 'private'` | ทดสอบบน Vercel |
| `file` | ไฟล์ในดิสก์ที่ `data/plans/<id>.json` | เซิร์ฟเวอร์ของสภาเภสัชกรรม |

ไม่ตั้งค่า: ใช้ `blob` เมื่อมี `BLOB_READ_WRITE_TOKEN` มิฉะนั้น `file`
`/health` รายงานว่ากำลังใช้อันไหน

ระบบจะย้ายไปอยู่กับสภาเภสัชกรรมในภายหลัง ที่เก็บจึงต้องเปลี่ยนได้ด้วยค่าตั้งค่าเดียว
ไม่ใช่การแก้โค้ดที่เรียกใช้

**คำขอเขียนพร้อมกัน** ทุก API เขียนเป็นการแก้ทีละรายการ เซิร์ฟเวอร์อ่าน–แก้–เขียนคืนเอง
หน้าเว็บไม่เคยส่งแผนทั้งฉบับกลับมาทับ ยังเหลือความเสี่ยงที่เจ้าหน้าที่สองคนกดในวินาทีเดียวกัน
แล้วฝ่ายหนึ่งถูกทับ — รับไว้ได้เพราะทีมมีไม่กี่คนและมักกดคนละร้าน โค้ดจะมีคอมเมนต์
`ponytail:` กำกับเพดานนี้และทางออก (ย้ายไป Postgres ถ้าจำนวนคนโต)

## 3. API

ทุกเส้นทางอยู่ใต้ `/api/plans` ใน `src/server.js`

| method | path | ทำอะไร |
| --- | --- | --- |
| GET | `/api/plans` | รายชื่อแผน: id, วันที่, จำนวนร้าน, จำนวนที่ตรวจแล้ว |
| GET | `/api/plans/:id` | แผนเต็ม |
| POST | `/api/plans` | สร้างแผน `{ date, title }` |
| DELETE | `/api/plans/:id` | ลบแผน |
| POST | `/api/plans/:id/items` | ใส่ร้าน `{ newCodes: [...] }` |
| PATCH | `/api/plans/:id/items/:newCode` | แก้ `status` / `note` / `order` / `pharmacists[].licenceNo` |
| DELETE | `/api/plans/:id/items/:newCode` | เอาร้านออก |
| POST | `/api/plans/:id/items/:newCode/sync` | ดึงข้อมูลร้านนี้จาก อย. ใหม่ |
| POST | `/api/plans/:id/pdf` | แผนเป็น PDF |
| POST | `/api/plans/:id/docx` | แผนเป็น Word |

### การใส่ร้านเข้าแผน

`POST /api/plans/:id/items` ทำงานหนักฝั่งเซิร์ฟเวอร์ ต่อหนึ่ง `newCode`:

1. `fetchDetail(newCode)` → ชื่อผู้รับอนุญาต เวลาทำการ พิกัด รายชื่อผู้มีหน้าที่ปฏิบัติการ
2. ต่อเภสัชกรหนึ่งคน `searchPharmacists({ firstName, lastName })` (มีแคชอยู่แล้ว)
3. เขียนลงแผนครั้งเดียว

ตอบกลับ `{ added: [...], failed: [{ newCode, message }] }` — ร้านที่ดึงไม่สำเร็จไม่ล้มทั้งชุด

### กติกาเติมเลข ภ.

ทะเบียนของสภาฯ ตอบได้หลายแถว จึงเติมเฉพาะกรณีที่ชี้ชัด

| ผลค้น | ทำ | `licenceSource` |
| --- | --- | --- |
| แถวเดียวที่ชื่อและนามสกุลตรงทั้งคู่ | เติมเลขนั้น | `auto` |
| หลายแถว | เว้นว่าง เก็บตัวเลือกไว้ให้เลือก | `ambiguous` |
| ไม่พบ หรือสภาฯ ไม่ตอบ | เว้นว่าง | `none` |
| เจ้าหน้าที่พิมพ์/เลือกเอง | ใช้ค่านั้น | `manual` |

เดาแล้วใส่เลขผิดลงเอกสารราชการเสียหายกว่าเว้นว่างให้คนเติม จึงไม่เดาเมื่อกำกวม

### การกั้นการเข้าถึง

เว็บเปิดสาธารณะบน Vercel รายชื่อร้านที่จะเข้าตรวจจึงรั่วได้ถ้าไม่กั้น
`/api/plans/*` ทุกเส้นทางต้องมีหัวข้อ `x-plans-passcode` ตรงกับ `PLANS_PASSCODE`
ถ้าไม่ตั้ง env นี้ ไม่กั้น (สะดวกตอนพัฒนาในเครื่อง) หน้าเว็บถามรหัสครั้งเดียวแล้วเก็บใน
`sessionStorage` ตอนย้ายไปสภาเภสัชกรรมค่อยเปลี่ยนเป็นระบบผู้ใช้จริง

## 4. หน้าจอ

ระบบยังไม่มี router และไม่เพิ่ม ใช้ `location.hash` สลับสองมุมมองใน `App.jsx`
`#/` = ค้นหาร้าน, `#/plans` = แผนการตรวจ Sidebar เพิ่มเมนู "แผนการตรวจ"

### หน้าค้นหา (ของเดิม)

- `ResultCard` เพิ่มช่องติ๊กเลือก การคลิกการ์ดยังเลือกร้านเดี่ยวเหมือนเดิม สองอย่างไม่ทับกัน
- `PickBar` แยกสองโหมด
  - เลือกร้านเดียว: ปุ่ม "กรอกฟอร์มการตรวจ" (เดิม) + "ใส่ในแผน"
  - เลือกหลายร้าน: "ใส่ N ร้านในแผน" พร้อมเลือกแผนที่มีอยู่ หรือสร้างแผนใหม่จากวันที่
- ร้านที่อยู่ในแผนแล้วขึ้นป้ายที่การ์ด กันใส่ซ้ำ

### หน้าแผนการตรวจ `#/plans`

- ซ้าย: รายชื่อแผนเรียงตามวันที่ พร้อมยอด "ตรวจแล้ว 3 / 7"
- ขวา: ตารางหกคอลัมน์ตรงกับไฟล์ Word ของสำนักงาน
- ต่อแถว: ช่องติ๊ก "ตรวจแล้ว", ปุ่ม "กรอกฟอร์ม", ปุ่มลบ, ลากเรียงลำดับ
- แถวที่ตรวจแล้วจางลงและติ๊กเขียว
- เลข ภ. ที่ `ambiguous` ขึ้นสีส้มพร้อมปุ่มเลือกจากรายชื่อที่สภาฯ ตอบมา
- เลข ภ. ที่ `none` ขึ้นปุ่มค้นใหม่และช่องพิมพ์เอง
- เภสัชกรหลายคนที่เวลาปฏิบัติการต่างกันขึ้นเตือนสีแดง เหมือนที่หน้ารายละเอียดร้านทำอยู่แล้ว
- ปุ่มหัวตาราง: "ส่งออก Word", "ส่งออก PDF", "อัปเดตข้อมูลจาก อย."

### บันทึกการตรวจ (`form.html`)

หน้าตาไม่เปลี่ยน ปุ่ม "กรอกฟอร์ม" ในตารางแผนส่ง `planId` เพิ่มไปกับข้อมูลที่ส่งต่อทาง
`localStorage` ซึ่ง `PickBar` ใช้อยู่แล้ว (ปุ่มเดิมบนหน้าค้นหาไม่มี `planId` เพราะไม่ได้มาจากแผน)
เมื่อกดสร้าง PDF หรือ Word สำเร็จ หน้าฟอร์มยิง
`PATCH /api/plans/:planId/items/:newCode { status: 'done', statusSource: 'auto' }`
ถ้าไม่มี `planId` (เปิดฟอร์มตรงๆ) ไม่ทำอะไร

สถานะที่เจ้าหน้าที่แก้เองกลายเป็น `statusSource: 'manual'` และการติดอัตโนมัติจะไม่ทับอีก
— คนย่อมรู้ดีกว่าระบบว่าตรวจจริงหรือยัง

## 5. การส่งออก

### PDF

หน้า `web/public/plan-print.html` กระดาษ A4 แนวนอน ฟอนต์ TH Sarabun ตารางหกคอลัมน์
เดินผ่าน puppeteer แบบเดียวกับบันทึกการตรวจ ใช้ทางเดินที่ `renderFormPdf` วางไว้แล้ว

### Word

`src/docx-plan.js` สร้าง `.docx` ขึ้นใหม่ด้วย `src/zip.js` ที่มีอยู่ ประกอบด้วยหัวเรื่อง
วันที่ และตารางหกคอลัมน์ ไม่ใช้ไฟล์ตัวอย่างของสำนักงานเป็นแม่แบบ เพราะไฟล์นั้นเป็น
แผนที่กรอกเสร็จแล้ว ไม่ใช่แม่แบบที่มีช่องว่าง การโคลนแถวจากมันจะเปราะกว่าการสร้างตารางเอง
และแม่แบบของบันทึกการตรวจต้องอยู่นอก git ต่อไปเหมือนเดิม (มีชื่อจริงเจ้าหน้าที่)

## 6. ความผิดพลาดที่ต้องรับมือ

| เจอ | ทำ |
| --- | --- |
| อย. ไม่ตอบ ตอนใส่ร้าน | ใส่เท่าที่ได้ ร้านที่พลาดขึ้นเตือนพร้อมปุ่มลองใหม่ |
| สภาฯ ไม่ตอบ ตอนดึงเลข ภ. | ร้านเข้าแผนตามปกติ เลข ภ. ว่าง `licenceSource: 'none'` |
| แผนวันเดียวกันซ้ำ | ต่อท้าย `-2`, `-3` |
| ใส่ร้านที่มีอยู่แล้วในแผน | ข้าม รายงานใน `failed` ว่าซ้ำ |
| ไม่มี blob token | ใช้ backend `file` โดยอัตโนมัติ บอกใน `/health` |
| รหัสผ่านผิด | 401 หน้าเว็บถามใหม่ |
| เขียนชนกัน | แก้ทีละรายการฝั่งเซิร์ฟเวอร์ มีคอมเมนต์กำกับเพดาน |
