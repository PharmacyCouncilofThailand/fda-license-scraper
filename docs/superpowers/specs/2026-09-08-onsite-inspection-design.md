# ตรวจหน้างานบนไอแพด — กรอกบันทึกทีละร้านจากแผนการตรวจ

วันที่: 8 กันยายน 2026

## ปัญหา

แผนการตรวจใช้งานได้แล้ว: เลือกร้านจาก อย. ใส่ลงแผนของวันนั้น พิมพ์ตารางถือไปตรวจ
แต่ *ตอนอยู่หน้าร้าน* ระบบยังช่วยอะไรไม่ได้ — `form.html` เป็นกระดาษ A4 ตายตัว
เปิดบนมือถือแล้วย่อจนตัวอักษรเหลือราว 4px ช่องกรอกจิ้มด้วยนิ้วไม่ได้จริง
เจ้าหน้าที่จึงยังจดใส่กระดาษที่ร้าน แล้วกลับมานั่งพิมพ์ซ้ำที่สำนักงาน

หน้าแผน (`#/plans`) เองก็เป็นตารางหกคอลัมน์กว้าง อ่านบนจอแคบไม่ได้เช่นกัน

## สิ่งที่จะสร้าง

1. หน้ากรอกบันทึกการตรวจสำหรับจอสัมผัส เข้าจากร้านในแผน กรอกทีละขั้น
2. ข้อมูลที่กรอกเก็บบนเซิร์ฟเวอร์ ผูกกับร้านในแผน กลับมากรอกต่อได้ ทีมเห็นชุดเดียวกัน
3. ถ่ายรูปแนบการตรวจ เลือกได้ว่าใบไหนแนบท้าย PDF
4. เซ็นชื่อบนจอ เลือกได้ทีละจุดจากแปดจุดในแบบฟอร์ม
5. เดินจากร้านหนึ่งไปร้านถัดไปในแผนได้จากในหน้า

## ขอบเขตที่ตัดออก

- **ไม่ทำ offline** — สำนักงานยืนยันว่ามีเน็ต 4G/5G ตลอดเวลาออกตรวจ ไม่ต้องมี PWA
  ไม่ต้องมีคิวซิงก์ ไม่ต้องสร้าง PDF ในเครื่อง
- **ไม่มีระบบผู้ใช้รายคน** — ยังกั้นด้วยรหัสผ่านเดียวของสำนักงานเหมือน `/api/plans/*`
  แต่ draft บันทึกชื่อเจ้าหน้าที่ที่เลือกจากรายชื่อไว้ ว่าใครเป็นคนกรอก
- **ไม่เช็คอินด้วย GPS**
- **Word ไม่มีรูปและไม่มีลายเซ็น** — เอกสารส่งจริงคือ PDF, Word มีไว้แก้ข้อความต่อ
  การฝัง media ลง .docx ต้องเขียน relationship กับ drawing XML ทั้งชุด ซึ่งไม่คุ้ม
  กับบทบาทของไฟล์นั้น
- **ไม่แก้หน้าตาของกระดาษ** — ทุกบรรทัดใน `form.html` อยู่บนกริดของไฟล์ Word ต้นฉบับ
  งานนี้เพิ่มได้แค่สิ่งที่ไม่ขยับมัน

## 1. ทางเลือกที่เลือก และทางที่ไม่เลือก

**เลือก: หน้ากรอกใหม่ใน SPA** — เพิ่ม route ในแอป React ที่มีอยู่ ใช้การนำทางแผน
ตัวเรียก API และการถามรหัสผ่านที่เขียนไว้แล้ว ส่วน `form.html` ไม่ถูกแตะในฐานะหน้ากรอก
— มันยังเป็นทั้งหน้ากรอกบนคอมและต้นฉบับที่ puppeteer พิมพ์ ตามเดิม

ไม่เลือก *ยัดโหมดมือถือเข้าไปใน `form.html`*: ไฟล์นั้นราว 2,000 บรรทัดและทุกบรรทัด
มีเหตุผลเรื่องการวางเส้นบนกระดาษ A4 การเพิ่ม UI มือถือ รูป และลายเซ็นเข้าไปอีกชั้น
ทำให้ไฟล์ที่เปราะที่สุดในระบบเปราะกว่าเดิม

ไม่เลือก *หน้า `mobile-form.html` แยกแบบไม่ใช้ React*: ต้องเขียนการนำทางแผน
การเรียก API และ state ใหม่ทั้งชุด ทั้งที่ SPA ทำไว้หมดแล้ว

ราคาของทางที่เลือกคือ **รายการช่องกรอกอยู่สองที่** — markup ใน `form.html`
กับ UI มือถือ — ซึ่งจ่ายไหวเพราะมีเทสต์บังคับให้ตรงกัน (ข้อ 5)

## 2. เส้นทางงานหน้างาน

1. `#/plans` เลือกแผนของวันนั้น (จอแคบกว่า 700px ตารางกลายเป็นการ์ดต่อร้าน)
2. แตะร้าน → `#/plans/:id/:newCode` หน้ากรอกของร้านนั้น
3. กรอกทีละขั้น autosave ขึ้นเซิร์ฟเวอร์
4. ถ่ายรูป เซ็นชื่อ ในหน้าเดียวกัน
5. กด "สร้าง PDF" — ได้ไฟล์จากทางเดิมทุกประการ และร้านติ๊ก "ตรวจแล้ว" อัตโนมัติ
6. ปุ่ม "ร้านถัดไป" พาไปร้านที่ยังไม่ตรวจในแผนเดียวกัน ไม่ต้องย้อนกลับหน้ารายการ

ร้านนอกแผนยังใช้ `form.html` ตรงๆ ได้เหมือนเดิม ไม่มี draft ไม่มีรูป กรอกแล้วสร้างไฟล์จบ

## 3. ข้อมูล

หนึ่งร้านในแผน = หนึ่งเอกสาร `records/<planId>__<newCode>.json`

```js
{
  planId: '2569-08-27',
  newCode: '…',
  officerName: 'นางสาวอชิดา บุญเพียร',   // ใครกรอก เลือกจากรายชื่อสำนักงาน
  values: { placeName: '…', inspectDate: '…', /* 89 คีย์ เท่ากับ collect() */ },
  checks: { shopOpen: true, /* 25 คีย์ */ },
  signatures: { page1: 'data:image/png;base64,…', duty: null, licensee: null,
                officer1: null, officer2: null, officer3: null,
                officer4: null, officer5: null },
  photos: [ { id, caption: '', inPdf: true, at: '2026-09-08T…' } ],
  createdAt, updatedAt
}
```

ไม่เก็บ draft ไว้ใน plan JSON เพราะ `list()` ของแผนอ่านทุกแผนทั้งฉบับ (หลังบ้าน blob
ดึงทีละไฟล์) เจ็ดร้านที่มีลายเซ็นห้าจุดจะลากไฟล์เป็นเมกะทุกครั้งที่เปิดหน้ารายการแผน

`values` และ `checks` ใช้คีย์เดียวกับที่ `form.html` ส่งออกจาก `collect()` ตรงตัว
เพราะปลายทางคือ `applyData()` ตัวเดิม — ไม่มีชั้นแปลงชื่อระหว่างกลาง มีแต่จะพัง

**รูปถ่าย** ตัวไฟล์ไม่อยู่ใน JSON: `photos[]` เก็บแค่ข้อมูลกำกับ ส่วนไบต์อยู่ใน
photo-store แยก คำบรรยายและ `inPdf` จึงแก้ไปพร้อม autosave รอบเดียว ไม่ต้องมี endpoint ของตัวเอง

## 4. ที่เก็บ

`plans-store.js` มีลอจิกสองหลังบ้าน (`file` / `blob`) ที่งานนี้ต้องใช้ซ้ำทั้งดุ้น
จึงดึงออกเป็นโรงงาน แล้วให้ทั้งสองที่เก็บเป็นเปลือกบาง

| ไฟล์ | หน้าที่ |
| --- | --- |
| `src/json-store.js` | โรงงาน: รับ prefix, โฟลเดอร์, และรูปแบบ id คืน `list/get/save/remove/backendName` |
| `src/plans-store.js` | เปลือก — ผิวนอกเหมือนเดิมทุกอย่าง ผู้เรียกไม่รู้ว่ามีอะไรเปลี่ยน |
| `src/records-store.js` | เปลือก — draft ของบันทึกการตรวจ |
| `src/photo-store.js` | ไบต์ของรูป: `put(planId, newCode, buffer) -> id`, `get`, `del`, `list` |

photo-store ใช้หลังบ้านเดียวกันโดยค่าตั้งค่าเดียวกัน:
`file` → `data/photos/<planId>/<newCode>/<id>.jpg`, `blob` → `photos/…` แบบ `access: 'private'`
รายชื่อร้านที่จะเข้าตรวจไม่ใช่ข้อมูลสาธารณะ รูปในร้านยิ่งไม่ใช่

`/health` รายงานหลังบ้านที่ใช้อยู่ เหมือนที่ทำกับแผน

## 5. รายการช่องกรอก และเทสต์ที่บังคับให้ตรงกัน

`web/src/lib/form-fields.js` เป็นรายการเดียวที่หน้ามือถือใช้ ต่อหนึ่งช่อง:

```js
{ name: 'dutyLicenseNo', step: 2, label: 'ใบอนุญาตเป็นผู้ประกอบวิชาชีพเภสัชกรรม เลขที่ ภ.',
  type: 'text' }              // text | number | date | time | textarea
```

และต่อหนึ่งกลุ่มติ๊ก:

```js
{ group: 'shopState', step: 3, label: 'สภาพร้านขณะตรวจ',
  options: [ { name: 'shopOpen', label: 'เปิดทำการตามปกติ' },
             { name: 'shopClosed', label: 'ปิดทำการ' } ] }
```

การจัดกลุ่มติ๊กมีความหมาย: `shopOpen`/`shopClosed` เป็นคู่ที่เลือกได้อย่างเดียว
บนกระดาษเป็นสองกล่องข้างกัน ซึ่งเจ้าหน้าที่ติ๊กผิดเป็นสองกล่องพร้อมกันได้
หน้ามือถือทำให้ผิดแบบนั้นไม่ได้

**`test-form-fields.js`** เปิด `public/form.html` อ่าน `name=` ของ `input.blank`,
`textarea.blank`, `.officer` และ `data-name=` ของ `.check` แล้วยืนยันสองทาง:
ทุกคีย์ในกระดาษต้องมีใน manifest และทุกคีย์ใน manifest ต้องมีในกระดาษ
เพิ่มช่องในกระดาษแล้วลืมใส่ในมือถือ เทสต์แดงทันที — นี่คือสิ่งที่ทำให้รายการสองที่จ่ายไหว

รายชื่อเจ้าหน้าที่ย้ายจากในตัว `form.html` ออกมาที่ `web/public/officers.js`
ให้ทั้งสองหน้าอ่านไฟล์เดียว แบบเดียวกับ `pharmacist-search.js` ที่ทำอยู่แล้ว

## 7. API

ทุกเส้นอยู่ใต้ `/api/plans/:id/items/:newCode/record` และผ่านการกั้นรหัสผ่านเดิม

| method | path | ทำอะไร |
| --- | --- | --- |
| GET | `/record` | อ่าน draft — ไม่มีก็คืนร่างว่างที่เติมข้อมูลร้านจากแผนให้แล้ว |
| PUT | `/record` | เขียน draft ทั้งฉบับ (autosave หน่วง 1 วินาที) |
| POST | `/record/photos` | อัปโหลดรูปหนึ่งใบ (`Content-Type: image/jpeg`, body ดิบ) ตอบ `{ id }` |
| DELETE | `/record/photos/:photoId` | ลบรูปหนึ่งใบ |
| GET | `/record/photos/:photoId` | ไบต์ของรูป |

**ทำไม PUT ทั้งฉบับ ไม่ patch ทีละช่อง** — คนกรอกร้านหนึ่งคือคนเดียว ณ เวลาหนึ่ง
ไม่ใช่กรณีเดียวกับแผนที่ทั้งทีมแตะพร้อมกัน แต่กันเขียนทับด้วย `updatedAt`:
คำขอส่งค่าที่อ่านมาไปด้วย ถ้าเซิร์ฟเวอร์มีของใหม่กว่า ตอบ 409 พร้อมฉบับล่าสุด
หน้าเว็บถามว่าจะทับหรือโหลดใหม่ — ดีกว่าเงียบๆ กินงานเพื่อน

**รูปดึงด้วย `fetch` แล้วทำเป็น object URL ไม่ใช่ `<img src>` ตรงๆ** เพราะแท็ก img
ส่งหัวข้อรหัสผ่านไม่ได้ และรหัสผ่านห้ามไปโผล่ใน URL

**ย่อรูปฝั่งเบราว์เซอร์ก่อนส่ง** — ด้านยาว 1600px, JPEG คุณภาพ 0.8 ทำให้ภาพจากกล้อง
ไอแพดราว 4MB เหลือราว 300KB ส่งบน 4G ทันใจและไม่ถมที่เก็บ เซิร์ฟเวอร์ปฏิเสธ body
ที่ใหญ่กว่า 5MB

## 8. ลายเซ็นและรูป ลงกระดาษ

**ลายเซ็น** วาดด้วยนิ้วบน canvas (pointer events) มีปุ่มล้าง ตัดขอบขาวก่อนเก็บ
เป็น PNG ราว 10–20KB ต่อจุด

ห้าจุดในแบบฟอร์มคือ `<span class="rule">` อยู่แล้ว เติมแค่ `data-sign="…"` ให้แต่ละอัน:

| `data-sign` | บรรทัด |
| --- | --- |
| `page1` | หน้า 1 — ลงชื่อ … เภสัชกร / ผู้รับอนุญาต / ผู้แทนผู้รับอนุญาต |
| `duty` | หน้า 2 คอลัมน์ซ้าย — ผู้มีหน้าที่ปฏิบัติการ / เภสัชกร |
| `licensee` | หน้า 2 คอลัมน์ซ้าย — ผู้รับอนุญาต / ผู้แทนผู้รับอนุญาต |
| `officer1`…`officer5` | หน้า 2 คอลัมน์ขวา — พนักงานเจ้าหน้าที่ ห้าแถว คู่กับช่องชื่อ `signOfficer1`…`signOfficer5` |

แปดจุด ไม่ใช่ห้า: ตารางลงชื่อของแบบฟอร์มมีแถวเจ้าหน้าที่ห้าแถวเพราะคณะที่ไปตรวจ
มีได้ถึงห้าคน หน้ามือถือจึงแสดงเฉพาะแถวที่มีชื่อเจ้าหน้าที่อยู่ ที่เหลือไม่ต้องเลื่อนผ่าน

attribute เปล่าไม่ขยับ layout และ `applyData()` วางรูปลายเซ็นทับด้วย
`position: absolute` จึงไม่กินที่ในสายการไหลของหน้า จุดที่ไม่ได้เซ็นบนจอเป็นเส้นว่าง
ให้เซ็นด้วยปากกาเหมือนเดิม

**รูปถ่าย** `form.html` ได้แผ่นที่สามเป็นภาคผนวก: หัวเรื่อง "ภาพถ่ายประกอบการตรวจ"
ชื่อร้านและวันที่ รูปสองใบต่อแถว คำบรรยายใต้รูป ล้นก็ขึ้นแผ่นถัดไปเอง
แผ่นนี้ซ่อนเมื่อไม่มีรูป เซิร์ฟเวอร์อ่านไบต์จาก photo-store แปลงเป็น data URL
ส่งเข้า `applyData()` — หน้าที่ puppeteer เปิดไม่ต้องต่อเน็ตเอง เหมือนที่ทำกับฟอนต์
และตราสภาฯ อยู่แล้ว

ฝั่งเซิร์ฟเวอร์ไม่ต้องแก้อะไรเพื่อรับหน้าที่เพิ่ม: แผ่นในหน้านี้สูงตามเนื้อหา
และมีกฎ `.sheet + .sheet { page-break-before: always; }` อยู่แล้ว แผ่นที่สาม
จึงขึ้นหน้าใหม่ของมันเองเหมือนแผ่นที่สอง

## 9. ความผิดพลาดที่ต้องรับมือ

| เจอ | ทำ |
| --- | --- |
| เน็ตหลุดตอน autosave | ปุ่มบันทึกขึ้นสีส้ม "ยังไม่ได้บันทึก — ลองใหม่" ค่าที่พิมพ์ยังอยู่ในหน้า ออกจากหน้าแล้วเตือนก่อน |
| อัปโหลดรูปไม่สำเร็จ | รูปใบนั้นขึ้นกากบาทพร้อมปุ่มลองใหม่ ใบอื่นไม่กระทบ |
| เปิดร้านเดียวกันสองเครื่อง | PUT ที่ `updatedAt` เก่ากว่าได้ 409 พร้อมฉบับล่าสุด ให้คนเลือกว่าจะทับหรือโหลดใหม่ |
| รหัสผ่านผิด | 401 → ถามรหัสใหม่แล้วยิงซ้ำ ทางเดิมที่ `plans-api.js` ทำอยู่ |
| กดสร้าง PDF ทั้งที่ยังกรอกไม่ครบ | สร้างให้ ไม่บล็อก แต่บอกว่าขั้นไหนยังว่าง — เจ้าหน้าที่รู้ดีกว่าระบบว่าอะไรจำเป็น |
| ไม่มี blob token | photo-store ใช้ `file` อัตโนมัติ บอกใน `/health` |
| รูปใหญ่เกิน 5MB | ปฏิเสธพร้อมข้อความบอกขนาด (ปกติไม่เกิดเพราะย่อฝั่งเบราว์เซอร์แล้ว) |

## 10. การทดสอบ

ตามแนวของโปรเจกต์ — สคริปต์ node ล้วน ไม่มี framework

- `test-form-fields.js` — manifest ตรงกับกระดาษทั้งสองทาง **ตัวกันหลักของทางเลือกนี้**
- `test-records-store.js` — เขียน/อ่าน/ลบ draft, `updatedAt` เก่ากว่าถูกปฏิเสธ 409,
  ลบรูปแล้วไบต์หายจริง, ไม่มี token ก็ตกไปหลังบ้าน `file`
- `test-form-parity.js` เดิมต้องยังผ่านทุกบรรทัด และเพิ่มกรณีใหม่: ยิง `applyData`
  พร้อมลายเซ็นห้าจุดกับรูปสี่ใบ แล้วยืนยันว่า **ตำแหน่งทุกย่อหน้าในหน้า 1–2
  ไม่ขยับแม้แต่พิกเซลเดียว** และมีแผ่นที่สามเพิ่มมา
- `smoke.js` — ต่อจากของเดิม: เขียน draft อัปรูปหนึ่งใบ สร้าง PDF แล้วตรวจว่าได้สามหน้า
